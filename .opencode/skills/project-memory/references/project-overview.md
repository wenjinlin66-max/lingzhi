# 项目总览

## 文件用途

用于描述本次比赛项目当前已经落地的最高层事实，而不是理想计划。

## 项目背景

- 赛题名称：**VibeChat — AI 驱动的情绪社交**
- 当前产品定位：围绕“情绪表达 → AI 理解 → 策略化匹配 → 匿名聊天”建立一个可演示的情绪社交 Web 应用。
- 当前实现强调：**先形成完整主链路，再逐步增强匹配策略和产品体验。**

## 当前核心目标

- 让用户输入当前情绪、状态或想说的话
- 调用 LLM API 返回结构化情绪分析结果
- 根据情绪返回多种房间匹配策略与房间建议
- 让用户以匿名身份进入房间进行文本聊天
- 保持本地可运行、可演示，并支持后续公网映射

## 非目标

- 不做完整社交关系链（好友、关注、长期身份体系）
- 不做复杂推荐基础设施、向量检索或长期记忆系统
- 不优先做重型后端工程化治理
- 不为了技术复杂度牺牲比赛时限内的稳定演示

## 范围边界

- 当前范围：`输入一句状态 -> 情绪分析 -> 分析页内完成匹配选择 -> 进入匿名房间 -> 发送消息`
- 当前重点：功能闭环、技术讲述性、产品感
- 当前技术栈：FastAPI + Next.js + PostgreSQL + Docker Compose

## 角色

- 用户：项目拥有者 / 参赛者
- Hephaestus / Sisyphus：规划、实现、同步项目记忆的执行助手

## 技术概况（按真实现状）

- 后端：FastAPI
- 前端：Next.js 14（App Router）
- 数据库：PostgreSQL
- 本地数据库运行方式：Docker Compose
- LLM 接口：
  - OpenAI 兼容接口（当前默认走老张 API）
  - Anthropic 标准接口
  - mock 演示兜底接口

## 当前已经落地的主链路

1. 首页 `/` 输入一句当前状态
2. 分析页 `/analyze` 调用 `/api/analyze` 获取结构化情绪分析结果
3. 分析页内直接继续调用 `/api/match` 获取多策略房间建议
4. 用户选择某个建议房间并进入 `/room/[roomId]`
5. 聊天页读取房间状态、历史消息，并通过 HTTP + WebSocket 完成匿名聊天

## 当前真实实现特征

- 匹配页 `/match` 已不是独立流程页，而是重定向到 `/analyze`
- 匹配结果当前以**策略分组的房间建议**为主，不是最终的人与房间双面板系统
- 匿名身份已经贯穿：`session_token -> nickname/avatar_color -> message`
- 聊天消息发送链路已打通，但消息历史和房间状态仍以轻量内存态为主
- 分析结果卡已经具备**基于主情绪 / 次情绪 / valence / arousal / intensity 的动态视觉主题**

## 当前已知现实约束

- `rooms`、`messages`、`emotion_analyses` 模型虽然存在，但当前运行时未完全落到真实持久化读写
- 匹配结果中的房间建议是服务端按规则合成的，不是从数据库真实检索出的房间池
- 前端和测试中有少量“超前字段/超前契约”，需要后续重新收敛

## 当前评审优势

- 功能性：主链路闭环已形成，不是单点 demo
- 技术性：LLM provider 分层清晰，前后端结构已分层，匿名身份链路已打通
- 用户体验：页面气质已明显产品化，分析卡具备情绪动态视觉表达

## 当前最大风险

- 线上演示地址尚未最终稳定固化
- 匹配逻辑还偏规则合成，离“更真实的人与房间匹配”还有差距
- 部分前端 / 测试契约比后端真实实现更超前，存在文档与代码不同步风险

## 当前整体状态

- 已完成：VibeChat 正式赛题方向收敛、前后端主链路骨架、老张 API 接入、匿名聊天基本闭环、动态情绪卡
- 进行中：项目记忆同步、匹配体验增强、首页创建房间/查找房间入口设计、分析页与匹配策略体验优化
- 未完成：公网稳定演示、房间真实持久化、匹配策略进一步升级
