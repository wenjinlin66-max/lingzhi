# 实施计划

## 当前计划状态

- 状态：正式赛题开发中
- 组织方式：比赛快速模式 + 前端主导
- 当前策略：**先保持分析/匹配/聊天闭环稳定，再增强多入口与多策略匹配表达**

## 当前真实执行路线

- 主入口仍然是“输入一句当前状态”
- 分析与匹配已经合并在 `/analyze` 页面中完成
- 房间进入后使用匿名身份直接聊天
- 当前匹配是**规则合成的多策略房间建议**，不是数据库驱动的真实房间检索

## 当前主执行方案

### 方案 A：策略化房间推荐（当前真实已实现的主路径）

当前已经落地：

- 首页输入心情
- 分析页返回结构化情绪卡
- 分析页内展示多策略房间建议
- 可按策略切换查看推荐房间
- 进入房间后进行匿名聊天

当前策略集合：

- 相似情绪
- 互补情绪
- 同频房间
- 多人情绪聊天室

当前优势：

- 对评审更有讲述性
- 比单一路由匹配更像产品
- 前端可以明确展示“多策略匹配”的产品表达

当前限制：

- 推荐结果仍然是规则生成，不是基于真实房间池检索
- 人与房间双重匹配还未完全实现

### 方案 B：真实房间池 / 人与房间双层匹配（当前未完成，作为下一阶段增强）

目标：

- 在现有多策略推荐基础上，增加：
  - 匹配人
  - 匹配房间
  - 创建房间
  - 查找房间

要补的后端支撑：

- 真实房间创建/加入接口
- 房间状态持久化
- 更明确的匹配 surface 契约（如 people / rooms）

要补的前端支撑：

- 首页新增“创建房间 / 查找房间”入口
- 分析页明确区分“匹配的人”和“匹配的房间”

## 当前真实页面链路

### 页面 1：首页 `/`

当前真实状态：

- 使用 `HomeEmotionForm`
- 保存 `draft.text`
- 点击后跳转 `/analyze`

当前待增强：

- 创建房间入口
- 查找房间入口

### 页面 2：分析页 `/analyze`

当前真实状态：

- 先分析情绪，再自动匹配
- 页面内同时承担：
  - 情绪结果展示
  - 匹配策略切换
  - 房间建议列表

当前待增强：

- 恢复/稳定 `AnalyzeResultFlow.tsx` 文件链路
- 收敛前端 `MatchResponse` 类型与后端真实契约
- 进一步把“匹配人 / 匹配房间”区分开

### 页面 3：匹配页 `/match`

当前真实状态：

- 已不是独立页面
- 当前只是 `redirect('/analyze')`

文档要求：

- 后续所有记忆文档都应把“匹配页”描述为**历史遗留路由**，而不是真实独立主流程页

### 页面 4：房间页 `/room/[roomId]`

当前真实状态：

- 拉取房间状态和历史消息
- 使用 WebSocket 感知进出房间系统消息
- 使用 HTTP 发消息
- 消息身份来自 session 持久化

## 当前后端最小接口集（真实）

- `GET /api/health`
- `GET /api/meta`
- `POST /api/analyze`
- `POST /api/match`
- `GET /api/rooms/{room_id}`
- `GET /api/rooms/{room_id}/messages`
- `POST /api/rooms/{room_id}/messages`
- `WS /api/rooms/{room_id}/ws`

## 当前已知差距

- `recommended_surface / surfaces` 还没有在后端正式实现
- `frontend/lib/types.ts` 与 `backend/tests/test_matching_api.py` 中存在超前字段
- `rooms/messages/emotion_analyses` 的数据库模型还没有完全成为运行时真实数据源
- 房间创建 / 查找房间功能尚未正式落地
